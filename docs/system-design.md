# 시스템 설계 문서 (system-design.md)

## 1. 과업 선정 및 정의
- **과업명:** 거래처 입금 시기 문의 메일 대필 ('정산 도우미')
- **업무 문제 및 목적:** 거래처에 세금계산서(청구서) 입금 일정을 문의할 때, 갑을 관계에서 상대방의 부담을 줄이면서도 요청 사항을 명확히 전달하는 정중한 비즈니스 메일을 작성한다.
- **타겟 사용자:** 거래처 입금 문의 메일 작성 시 어조 조절(독촉처럼 느껴지지 않는 표현)에 부담을 느끼는 실무자.
- **입력 데이터 형태:** 거래처명, 담당자명, 청구(세금계산서) 발행일, 청구서 번호, 이전 문의 여부, 요청 (실무 활용 시 청구서 번호는 사용자가 정확히 기재하는 것을 기본 전제로 함)
- **출력 규격:** 제목, 인사, 본문(3~4문장), 맺음말, 서명(`[이름]`) 순서의 부드러운 비즈니스체 메일
- **선정 모델:** GPT-6

---

## 2. 페르소나 설계
- **이름:** 정산 도우미
- **역할:** 거래처에 보내는 입금 시기 문의 메일을 대신 써 주는 작성 담당
- **전문 분야:** 갑을 관계에서 상대방의 부담을 줄이는 정중한 비즈니스 문의 표현
- **말투:** 부드러운 비즈니스체 (먼저 양해를 구한 뒤 요청은 분명하게 적음)
- **금지 사항:** 입력에 없는 날짜·금액·번호를 임의로 만들지 않음. `"독촉"`, `"지연"`, `"미납"`, `"빨리"` 같은 단어를 쓰지 않음. 입금 기한이나 법적 조치를 언급하지 않음.
- **우선순위:** 사실 정확성 > 독촉처럼 느껴지지 않는 어조 > 형식

## 4. 프롬프트 개선 이력 (v1 → v2)
- **무엇을 고쳤는가:** 시스템 프롬프트 v1의 입력 설명과 출력 형식 사이에 **`입력 확인`** 규칙 단락을 추가하여 v2를 작성했다. (필수 5개 항목 중 누락 시 메일 작성을 멈추고 되묻도록 지시, 특히 청구서 번호 확인 강조)
- **수정 이유 (직접 작성):** v1에는 필수 정보가 비었을 때의 처리 규칙이 없었다. 그래서 Zero-shot 실행(로그 턴 6)에서 청구서 번호가 비어 있는데도 바로 메일을 썼다. 같은 거래처에 거래가 여러 건이거나 한 번에 여러 건을 발행하는 경우, 번호 없이는 어느 청구건인지 특정되지 않아 요청 내용을 명확하게 쓸 수 없다. 그래서 v2에는 비어 있는 항목이 있으면 메일을 쓰지 않고 되묻는 규칙을 추가했고, 번호를 특히 확인하도록 했다.

## 5. Few-shot 예시 (3건)

### 예시 1 (신규 문의)
- **입력:**
```text
거래처명: 한빛상사
담당자명: 김민재 과장님
청구(세금계산서) 발행일: 2026년10월05일
청구서 번호: INV-2026-0142
이전 문의: 없음
요청: 대략적인 입금 시기를 묻는 메일을 작성해 주세요.
```
- **출력:**
```text
제목: [문의] 청구서 INV-2026-0142 관련 입금 일정 확인 부탁드립니다

김민재 과장님께,
안녕하세요. 늘 도움 주셔서 감사드립니다.

바쁘신 중에 번거롭게 해 드려 죄송합니다. 2026년10월05일에 발행해 드린 청구서(INV-2026-0142)와 관련하여, 입금 일정이 어느 정도로 잡혀 있는지 여쭙고자 연락드렸습니다. 정확한 날짜가 아니더라도 대략적인 시기(예: 이번 달 말, 다음 달 초)를 알려 주시면 내부 정리에 큰 도움이 되겠습니다. 편하신 때에 회신 주시면 감사하겠습니다.

항상 감사드립니다.
[이름] 드림
```

## 6. 프롬프트 기법 비교 및 단계적 추론 유도 여부

### 6.1. Zero-shot vs Few-shot 실행 비교

| 비교 항목 | Zero-shot (v1만 입력) | Few-shot (v1 + 예시 3건) |
| :--- | :--- | :--- |
| **입력 B 번호 누락 대응** | 되묻지 않고 번호 언급을 생략한 채 메일 바로 작성 | 메일을 쓰지 않고 누락된 번호를 되물어 확인 후 작성 |
| **출력 형식 일관성** | 입력 A는 라벨(`인사`, `본문`) 표기, 입력 B는 이메일 카드 형태로 불일치 | 입력 A·B 모두 예시와 동일한 `제목-인사-본문-서명` 구조 유지 |
| **발행일 표기** | `2026년 11월 3일` 형태로 띄어쓰기 변형 | 입력 표기(`2026년11월03일`) 그대로 유지 |
| **실무 활용 관점** | 예시 입력 번거로움이 없으나, 누락 항목이 있을 때 임의 작성 위험 존재 | 누락 항목 확인 안전장치가 작동하나, 매번 예시를 포함해야 하는 번거로움 존재 |

- **비교 평가 및 결론:** Zero-shot은 형식이 일정하지 않고(1건은 라벨 표기, 1건은 이메일 카드 형식) 필수 정보가 비어 있어도 임의로 메일을 작성하는 한계가 있었다. 같은 거래처·같은 날짜에 세금계산서를 여러 건 발행하는 실무 상황에서는 청구서 번호 없이는 어느 건인지 알 수 없으므로, 모르는 것은 임의로 작성하지 않고 확인 후 작성하는 Few-shot의 동작이 안전하다. 실무에서는 사용자가 어느 건인지 청구서 번호까지 정확히 기재하는 것을 전제로 Zero-shot(v2 프롬프트 적용)을 활용하되, 시스템 프롬프트에 되묻기 규칙을 직접 반영하여 예시 없이도 안전장치가 작동하도록 설계했다.

### 6.2. 단계적 추론 유도 추가 여부
- **적용 여부:** 추가하지 않음.
- **사유:** 실행 로그 기준 모델이 입력값을 틀린 적이 없고, 환각 검증 질문 5건 모두 Pass로 확인되어 별도의 단계적 추론 유도 문구는 불필요하다고 판단함.

## 7. 검증 전략 및 환각 검증 판정

### 7.1. 사전 검증 전략 및 Pass/Fail 기준
- **사실 오류 의심 기준:** 입력에 없는 날짜·금액·청구서 번호·입금 기한·법적 조치를 지어내거나, 이전 문의 내역·담당자 직함을 다르게 적는 경우 사실 오류(환각)로 의심한다. 단, 날짜 값이 입력과 일치하면 띄어쓰기 변형(`2026년11월17일` → `2026년 11월 17일`)은 허용한다.
- **Pass/Fail 판정 기준:** 아래 기준 A 또는 기준 B 중 하나 이상 충족 시 Pass, 둘 다 충족하지 못하면 Fail로 판정한다.
  - **기준 A:** 정답을 맞히고 근거를 함께 제시했다.
  - **기준 B:** 모를 때 모른다 또는 확인 필요를 밝히고 확인 절차를 제안했다.

## 8. v3 개선 이력 및 테스트 상태

### 8.1. 개선 목적
- **관찰된 개선 후보:** 입금 시기 문의 메일에서 문의 의도, 배려/사과, 회신 요청 표현이 겹쳐 문장이 불필요하게 길어질 수 있음.
- **근거:** 2026년 11월 23일 동원산업 테스트 출력에서 ‘문의드리고자 연락드립니다’, ‘입금 예정 시기를 확인해 주실 수 있을까요’, ‘확인 가능하실 때 회신 주시면’ 등 문의 및 확인 표현이 겹치는 양상이 관찰됨. 한 번의 결과이므로 반복적 문제로 확정하지 않고 개선 후보로 둠.
- **개선 방향:** 정중함은 유지하되, 같은 의미의 문의·배려·감사 표현을 반복하지 않고 핵심 요청을 간결하게 전달하도록 규칙을 추가함.

### 8.2. v3 프롬프트 등록 위치
- 시스템 프롬프트 v3 본문은 프롬프트 구성 섹션인 **3.3**에 [카테고리: 페르소나]로 등록함.
- 이 8번 섹션에는 v3 추가 사유, 변경 이력, 검증 상태만 기록하며 프롬프트 본문을 중복 수록하지 않음.

### 8.3. 변경 이력 (v2 → v3 후보)
- **추가한 규칙:** 동일 의미의 문의·배려·감사 표현 반복을 줄이고, 불필요한 부연을 최소화하는 간결성 규칙.
- **수정 이유:** v2를 사용한 실제 테스트에서 문의 목적과 확인/회신 요청, 배려 표현이 겹쳐 문장이 길어지는 경향이 관찰됨.
- **검증 상태:** 아직 재테스트 전. v3는 개선 후보이며 최종 적용 버전으로 확정하지 않음.
- **테스트 원칙:** v2의 기존 결과를 기준으로 비교하고, 새 채팅에서 v3를 적용해 동일한 테스트 입력을 실행한다. 실제 출력에서 중복 표현이 줄었는지 확인한 뒤 채택 여부를 결정한다.
